# Аудит сайта leshalarin.ru

Дата: 21.05.2026
Цель аудита: оценить, насколько сайт решает свои задачи (продажи курсов, заявки на консультации, рост блога/аудитории), и собрать конкретные правки.

Стек: Astro (SSR, Node adapter) + Go API + Postgres, единый домен через nginx.
Палитра: navy `#1a2744` / orange `#e8652a` / cream `#f8f5ef`. Шрифты: Cormorant Garamond + Manrope.

---

## 0. Воронка сайта — общая картина

Маркетинговые страницы и цели:

| Страница | Что должна делать |
|---|---|
| `/` (index) | Продавать «Личное ведение» — сейчас CTA = «лист ожидания» (Telegram) |
| `/consultation` | Записывать на платную консультацию 5 000 ₽ — CTA в Telegram |
| `/course` (legacy) и `/courses/myagkiy-start` (новая) | Захватывать лид на бесплатный курс — две версии той же страницы |
| `/courses/zdorovaya-spina` | Продавать платный курс (3 990 / 12 990 ₽) — кнопки `data-tariff` без обработчика |
| `/results` | Социальное доказательство |
| `/blog/*` | Привлекать SEO-трафик и подогревать к курсу |
| `/salut-2026` | Лендинг под отдельную аудиторию («Здоровая спина в Салюте») |
| `/cabinet/*`, `/auth/*` | Удерживать клиента после регистрации/оплаты |

Главная проблема воронки: **почти все CTA на маркетинговых страницах уводят пользователя в Telegram/Max**, а не в форму на сайте. Это:
- ломает измеримость (нет ни одной воронки, которую можно было бы посчитать в аналитике без UTM-меток на ссылках);
- ведёт к утечке холодного трафика, у которого нет Telegram;
- мешает прогревать через email/CRM, потому что почта вообще не собирается;
- ставит весь бизнес в зависимость от одного канала.

На страницах с реальной онлайн-продажей (платный курс «Здоровая спина», бесплатный «Мягкий старт») инфраструктура уже есть — Astro + API + Prodamus. Но к ней не подведены кнопки и копирайт.

## 1. Сквозные проблемы (касаются нескольких страниц)

### 1.1. SEO/meta — минимальный набор отсутствует

В `web/src/layouts/SiteLayout.astro` и `web/src/layouts/Base.astro`:
- нет `<meta property="og:*">` и `<meta name="twitter:*">` → при шере в TG/VK/чате нет превью (заголовок + картинка + описание);
- нет `<link rel="canonical">` — будут дубли в индексе (`/course` и `/courses/myagkiy-start` — одна и та же страница);
- `description` по умолчанию слишком общий и одинаковый: «Личное ведение, бесплатный курс, статьи и результаты учеников».

В `web/public/` нет:
- `robots.txt` (как минимум разрешить индексацию, отключить `/cabinet`, `/admin`, `/api`);
- `sitemap.xml` (со списком статей блога — основной канал для SEO);
- `site.webmanifest` (PWA-friendly, можно отложить).

Структурированные данные (JSON-LD) отсутствуют:
- `Person` на главной (тренер);
- `Article` на статьях блога (даты, автор, картинка);
- `Course` на страницах курсов (цена, длительность, формат, оценки);
- `FAQPage` для FAQ на странице курса;
- `BreadcrumbList` на статьях и уроках.

Без этого Яндекс/Google не покажут rich snippets — отказ от бесплатного канала роста.

### 1.2. Безопасность HTTP

`nginx/nginx.conf` слушает только `:80`. Нет HTTPS:
- Cookies `access_token`, `refresh_token`, `csrf` ставятся без `Secure`;
- Браузеры всё больше блокируют не-HTTPS аутентификацию;
- Google использует HTTPS как ранжирующий сигнал.

В nginx нет `Content-Security-Policy` и `Strict-Transport-Security`, хотя они подготовлены в `PROMPT.md`. Без CSP любой XSS даёт полный доступ к токенам через куки/JS.

### 1.3. Шрифты — внешний CDN

`fonts.googleapis.com` подключается из обоих layouts. Есть `preconnect`, но это всё равно сторонний запрос, FOUT на медленных сетях и зависимость от Google. В РФ это медленно/нестабильно. Лучше self-hosted `woff2` с `font-display: swap` (через `astro/font` или просто положить файлы в `public/fonts/`).

### 1.4. Дублирование стилей в layouts

`SiteLayout.astro` и `Base.astro` несут практически одинаковые ~50 строк CSS для `.site-nav`, `.site-footer`, `.btn`, `.container`. При любой правке навигации нужно править в двух местах. Решение: вынести общие токены и компоненты в один CSS-модуль (например, `src/styles/site.css`) и подключать обоими layout'ами.

### 1.5. Доступность (a11y) — несколько системных пробелов

- Все `alt` у фото Алексея — буквально «Алексей Ларин». Для SEO/a11y лучше: «Тренер Алексей Ларин ведёт занятие со взрослой ученицей» и т.п. Конкретный alt = плюс к индексации image search.
- Нет `prefers-reduced-motion` ни в одном animation-блоке — у людей с вестибулярными проблемами hero «прыгает».
- Кнопки `<a href="#" data-tariff="...">` в `legacy/zdorovaya-spina.html` не имеют видимого handler'а (в Astro-обёртке `pages/courses/zdorovaya-spina.astro` я не вижу скрипта обработки `data-tariff`). Это критично — основная кнопка покупки курса.
- `focus-visible` стили есть местами (`.ms-btn-hero`, `.tg-strip-btn`), но не на всех CTA. Клавиатурная навигация неровная.

### 1.6. Один и тот же контент дублируется в `legacy/` и в Astro

- `course.html` (через `pages/course.astro`) + `pages/courses/myagkiy-start.astro` — одна страница, два URL, разный UX, разные формы регистрации.
- `index.html` (через `pages/index.astro`) — лендинг лично��о ведения, существует в одном экземпляре.
- `zdorovaya-spina.html` + `pages/courses/zdorovaya-spina.astro` — то же самое: legacy-HTML рендерится в Astro, но кнопки покупки (`data-tariff`) не подключены к API.

Это и есть техдолг: легаси-HTML «склеен скотчем» через `extractLegacy + ?raw`. Внутри каждой legacy-страницы — свой `<nav>` (вырезается regex'ом), свой `<footer>` (вырезается), свой `<style>` (инлайнится в `<style is:global>`). Из-за этого:
- невозможно нормально менять навигацию (нужно править и общий `SiteHeader.astro`, и legacy-навигацию для случаев когда regex не сработает);
- стили перекрывают друг друга (`.hero`, `.btn-hero` существуют у каждой страницы);
- актуальные правки (например, цена консультации) живут в HTML, а не в БД.

### 1.7. Статические объявления, которые устаревают

В `legacy/index.html`, `legacy/consultation.html`, `legacy/course.html` зашиты тексты «Сейчас места заняты — следующий набор открывается в сентябре. Летом я тренирую детей в детском лагере». После сентября эти блоки будут смущать пользователей. Решение:
- вынести «статус набора» в `.env` или (лучше) в админку как поле `settings` в БД;
- рендерить разный текст в зависимости от состояния «открыт / лист ожидания / закрыт».

### 1.8. Утечка dev-данных в проде

В `pages/auth/register.astro` сообщение об успехе включает `j.verify_link_dev`:
```js
msg.innerHTML = 'Аккаунт создан. ... <br/>Dev-ссылка для подтверждения: <a href="' + j.verify_link_dev + '">'+j.verify_link_dev+'</a>';
```
Если API возвращает эту ссылку и в проде (а он будет, если SMTP не настроен), реальные пользователи увидят свою verify-ссылку прямо в UI. Это и баг UX, и потенциальный security-issue (видна часть auth-флоу). На фронте нужно показывать `verify_link_dev` только если `import.meta.env.DEV` или `j.environment === 'development'`.

То же в `forgot.astro` — `j.reset_link_dev` показывается всегда.

### 1.9. Файлы курса лежат публично

`pages/cabinet/zdorovaya-spina.astro` ссылается на `/files/metodichka.pdf`, `/files/kalendar.pdf`, `/files/zamery.pdf` — это файлы в `web/public/files/`. Они доступны кому угодно по прямому URL без enrollment. Если они и правда часть платного курса, материалы нужно отдавать через защищённый эндпоинт (по аналогии с видео — `auth_request` в nginx + Go проверяет enrollment).

### 1.10. Прочие технические детали

- `middleware.ts` дёргает `/api/me` на **каждом** запросе, включая `/blog/[slug]` и `/salut-2026`, где user не используется. На холодной странице это +50–100ms к TTFB. Стоит вызывать `/me` только когда `(context.locals as any).needsUser` или просто пропускать неавторизованные routes по списку.
- `apiJson('/api/me', { cookie })` без таймаута — если API лежит, фронт виснет.
- `html { overflow-x: hidden }` маскирует возможные проблемы с горизонтальным скроллом — лучше найти, что выходит за viewport, и поправить.
- Брейкпоинты в legacy CSS — почти все на `max-width: 700px`. Между 700 и 1100 страницы будут выглядеть «сжато».
- В hero-секциях `min-height: 100vh` — на мобильных с панелью браузера это даёт «слишком высокий первый экран», лучше `min-height: 100svh`.

## 2. Разбор по страницам

### 2.1. Главная `/` — «Личное ведение»

**Файлы:** `pages/index.astro` → `legacy/index.html` через `extractLegacy`.

**Что хорошо:**
- Чёткое позиционирование: «Через 3 месяца вы будете другим человеком».
- Личная история (перелом 3 позвонков в 9 лет) — отличный social proof.
- Сильные секции: Problems → Story → Format (5 шагов) → Journey (4 месяца) → Results → Reviews → CTA.
- Хорошие визуальные ритм и типографика.
- Структурированные стейтменты («8000+ через проекты», «65+ отзывов», «8 лет практики»).

**Что мешает задаче (продажи личного ведения):**
1. **Нет цены.** В блоке «Цена и запись» написано «Стоимость обсудим на первом созвоне». На холодный трафик это снижает конверсию в 2–3 раза. Сравните с консультацией, где цена 5 000 ₽ показана явно — там понятен порог.
2. **CTA = «Записаться в лист ожидания»** → ведёт в Telegram (`https://t.me/larin_lesha`). Сайт не собирает email/телефон. Если человек закрыл вкладку — он потерян.
3. **Hero-notice** про «осенний набор» зашит в HTML. После сентября станет ложным.
4. **Нет H1 в шапке** в обычном смысле — заголовок `<h1>Через 3 месяца вы будете другим человеком</h1>` лежит внутри hero и виден только после загрузки. SEO-парсер найдёт его, но лучше держать его в начале документа.
5. **Anchor-nav вырезается** в `legacy.ts` через regex (`reAnchorNav`) — на сайте якорная навигация отсутствует, хотя она была полезна (Problems → Story → Format → Results → CTA). Стоит вернуть её через Astro-компонент.
6. **Кнопка «Записаться в лист ожидания»** в hero ведёт на `#cta` (то есть прокрутка вниз), а в самом CTA блоке — на `https://t.me/larin_lesha`. Это две разные кнопки с одним и тем же лейблом — пользователь может запутаться.
7. **`.btn-hero` показывает текст «Записаться в лист ожидания →»**, но это не лист ожидания на сайте, а просто переход в TG. Если перевести «список ожидания» в реальную форму на сайте (имя+email+коротко запрос → запись в `leads` таблицу + письмо админу) — увеличение конверсии будет ощутимым.

**Конкретные правки:**
- Добавить мини-форму захвата лида: имя + email + 1 строка про запрос → `POST /api/leads` (создать таблицу `leads(id, email, name, message, source, created_at)` и админский раздел `/admin/leads`). Кнопка «В TG» — вторая опция.
- Указать «вилку» цены или хотя бы примерный диапазон (например, «От N₽/мес — обсудим точную программу на первом созвоне»). Это снимает страх «дорого/дёшево» у тех, кто не готов писать в TG ради вопроса о цене.
- Hero-блок «Сейчас места заняты» вынести в data из БД/env, чтобы не править HTML каждый сезон.
- Вернуть anchor-nav как Astro-компонент.
- Добавить структурированные данные `Person` (Алексей, образование, опыт).
- Добавить OG-теги и фото для шеринга.
- Сделать `description` уникальным под главную: цифры (8 лет, 8000+, формат — онлайн, фокус — мягкий старт без боли).

### 2.2. `/consultation`

**Файлы:** `pages/consultation.astro` → `legacy/consultation.html`.

**Что хорошо:**
- Прозрачная цена (5 000 ₽, 55 минут).
- Чёткий формат «как проходит созвон» (3 этапа).
- Один отзыв и блок «что получите».
- Honesty: «4–5 в месяц провожу».

**Что мешает задаче (лиды на консультацию):**
1. CTA снова **только Telegram**. Здесь это особенно странно, ведь оплата в 5 000 ₽ может идти прямо через Prodamus.
2. **Нет онлайн-оплаты.** Это легко, потому что Prodamus уже подключён. Можно сделать `POST /api/consultations/checkout` с фиксированной суммой и возвратом ссылки на оплату.
3. **Лист ожидания на сентябрь** — снова статичный текст.
4. **Нет блока «после оплаты»**: когда придёт ссылка на Zoom, как готовиться, что взять.
5. Отзывов очень мало (1) — для конверсии «холодного» лида на 5 000 ₽ это маловато. Стоит добавить ещё 2–3 коротких.

**Конкретные правки:**
- Кнопка «Оплатить и записаться» (5 000 ₽) через Prodamus + форма-анкета сразу после оплаты (на странице `/cabinet/consultation` или письмом).
- Telegram оставить как «есть вопрос — напишите в TG», но не как основной CTA.
- FAQ: «можно ли вернуть деньги», «если не подойдёт время», «как готовиться».
- OG-теги с фото Алексея.

### 2.3. `/course` (legacy) и `/courses/myagkiy-start` (новый)

**Файлы:** `pages/course.astro` → `legacy/course.html` и `pages/courses/myagkiy-start.astro`.

Это **две версии одной и той же страницы** с разным флоу:
- `/course`: quick-signup (имя+email+опц.телефон) → создаёт аккаунт, шлёт пароль письмом, редиректит в `/cabinet/myagkiy-start`. Самый low-friction вариант.
- `/courses/myagkiy-start`: уже залогиненный пользователь жмёт «Получить доступ» → `enroll-free`. Если не залогинен — «Войти/Зарегистрироваться» через стандартный auth.

**Что хорошо:**
- `/course` — самый правильный low-friction флоу на сайте: 2 поля, доступ сразу.
- На обеих страницах хороший список уроков.
- Тонкие штрихи: бесплатно навсегда, без спама.

**Что мешает задаче:**
1. **Дублирование путей** ломает SEO (две страницы с почти идентичным контентом). Нужен либо canonical с `/courses/myagkiy-start` на `/course`, либо один из URL должен 301-редиректить на другой. На уровне UX тоже непонятно, почему ссылка в navbar ведёт на `/course`, а из каталога — на `/courses/myagkiy-start`.
2. **После регистрации через quick-signup пользователю не показан его пароль.** Письмо может прийти позже / в спам / не прийти. Решение: в success-state показать «Аккаунт создан. Email: X. Пароль отправлен на почту. Сохраните или войдите сейчас». Опционально — позволить установить свой пароль прямо в форме.
3. **На /courses/myagkiy-start кнопка «Получить доступ» — POST /enroll-free** без подтверждения. Полностью ок для UX, но имеет смысл сначала проверить `email_verified`.
4. Cекция "Видео добавляются в ближайшее время" — если уроков пока нет, она снижает доверие. Стоит либо добавить уроки, либо переписать в «8 практик-уроков с короткими видео и описанием упражнений».

**Конкретные правки:**
- Выбрать один canonical URL для «Мягкого старта». Я бы оставил `/course` как короткий маркетинговый адрес и сделал 301 с `/courses/myagkiy-start` на `/course`.
- В success-state quick-signup показать email + сгенерированный пароль (одноразово, с инструкцией сохранить).
- Объединить две страницы в одну: текущий `/course` (legacy) — хорош как лендинг, а `/courses/myagkiy-start` после оплаты/регистрации сразу редиректить в `/cabinet/myagkiy-start`.

### 2.4. `/courses/zdorovaya-spina` — платный курс

**Файлы:** `pages/courses/zdorovaya-spina.astro` → `legacy/zdorovaya-spina.html` (+ скрипт, который скрывает тарифы для уже купивших).

**Что хорошо:**
- Самая «продающая» структура: hero → problems → story → program (5 модулей) → included → results → tariffs → guarantee → FAQ → final CTA.
- Два тарифа (3 990 / 12 990) с явной разницей.
- Гарантия возврата 7 дней.
- Sticky guarantee box рядом с FAQ — хорошее решение.

**Что мешает задаче:**
1. **Главная проблема:** кнопки «Купить за 3 990 ₽» / «Купить за 12 990 ₽» — это `<a href="#" data-tariff="self">` без JS-обработчика в `pages/courses/zdorovaya-spina.astro`. Я не вижу слушателя `click` на `data-tariff` — то есть кнопки покупки не работают. Это критический баг.
2. Для двух тарифов нужны два курса/SKU в БД и два checkout-эндпоинта или один с параметром `tariff=`. Сейчас в `pages/courses/[slug].astro` есть generic `POST /api/courses/${slug}/checkout`, но он на один тариф.
3. Стиль «Здоровая спина за 3 недели» — медицинское обещание. Юридически рискованно. Стоит мягче: «За 3 недели наладите регулярность» / «За 3 недели сформируете привычку».
4. В hero `«Гарантия возврата 7 дней · оплата через Prodamus»` — упоминание Prodamus до знакомства с продуктом снижает доверие (звучит как «не моя касса»). Лучше «Безопасная оплата картой».
5. **«Стоимость обсудим на первом созвоне» нет, цена явная** — это плюс. Но второй тариф 12 990 ₽ требует личного чата 3 недели + 45–60 минут созвон. Это много времени, при 4–5 консультациях в месяц у Алексея может не хватать ёмкости. Стоит явно ограничить «осталось N мест в этом месяце» (с реальным счётчиком из БД).

**Конкретные правки:**
- Подключить кнопки `data-tariff` к API: завести два курса в БД (`zdorovaya-spina-self`, `zdorovaya-spina-support`) или передавать тариф в `/api/courses/zdorovaya-spina/checkout?tariff=self`. На фронте — JS-обработчик в `.astro`-обёртке.
- Переписать `H1` без медицинских обещаний.

### 2.6. `/blog` и `/blog/[slug]`

**Файлы:** `pages/blog/index.astro`, `pages/blog/[slug].astro`. Данные из API, статьи сидятся из `api/internal/seed/articles_html/` (32 статьи).

**Что хорошо:**
- Чистая сетка с тегами и фильтром (JS).
- Полный layout с meta, reading time, cover image, CTA в конце.
- В конце статьи — `article-cta-final` (бесплатный курс) + `tg-inline` (канал).

**Что мешает задаче (SEO + удержание):**
1. **Нет sitemap.xml** — все 32 статьи могут не попасть в индекс быстро.
2. **Нет `Article` JSON-LD** (автор, дата публикации, картинка) — Яндекс/Google ставят такие статьи ниже.
3. **Нет связанных статей** в конце поста. У читателя только один следующий шаг: курс. Нужно ещё «Похожие статьи» (по тегу).
4. **Нет дат публикации/обновления** в UI. Для блога это важно (в т.ч. для пользователя).
5. **Filter работает только клиентским JS**: при выборе тега URL не меняется, поделиться отфильтрованным списком нельзя.
6. **OG-теги по статьям** — отсутствуют. Если кто-то шерит статью в TG/VK, превью будет дефолтное.
7. **`set:html` на body статей** — на странице рендерится сырой HTML из БД. Нужно проверить, что в админ-эдиторе нет возможности вставить произвольный JS — иначе XSS через статью.
8. **excerpt не везде есть** — это видно в карточках («Читать» вместо описания). На карточке без описания читатель не понимает, о чём статья.

**Конкретные правки:**
- Сгенерировать `sitemap.xml` (например, через Astro endpoint `pages/sitemap.xml.ts`, читающий список slug'ов из БД).
- Добавить `Article` JSON-LD в `pages/blog/[slug].astro` (используя `a.author`, `a.published_at`, `a.cover_image_url`).
- Добавить блок «Похожие статьи по тегу» (3–4 карточки) перед CTA.
- Показать дату публикации/обновления.
- Фильтр тегов → query-param `?tag=energy`, SSR-генерация.
- Канонические URL для статей.
- Sanitize HTML статей перед сохранением в БД (DOMPurify / bluemonday на бэкенде).

### 2.7. `/cabinet/*`

**Файлы:** `pages/cabinet/index.astro`, `courses.astro`, `settings.astro`, `myagkiy-start.astro`, `zdorovaya-spina.astro`.

**Что хорошо:**
- Прогресс-бары по курсам.
- Кастомные страницы курсов с уроками + материалами (для Здоровой спины — материалы PDF).
- Settings содержит смену пароля.

**Что мешает задаче (удержание):**
1. **`/cabinet` минималистичен**: имя пользователя, alert о подтверждении email, список курсов. Нет блока «Продолжить с того же места», нет последнего пройденного урока. Между тем это первое, что хочется видеть.
2. **Smart-redirect**: ссылка на курс `myagkiy-start` ведёт в `/cabinet/myagkiy-start`, а `zdorovaya-spina` — почему-то на публичную страницу `/courses/zdorovaya-spina` (см. `cabinet/index.astro:15`). Это путаница.
3. **Письмо «Доступ открыт»** — нужно проверить, что оно действительно отправляется и содержит ссылку на `/cabinet/<slug>`. Если нет — пользователь после оплаты не понимает, где курс.
4. **Settings.astro** — нельзя поменять email/имя без подтверждения. Это норм с т.з. безопасности, но нужно явное сообщение.
5. **Файлы курса `/files/*.pdf`** доступны публично (см. 1.9).
6. **Нет страницы «Сертификат» / «Завершение»** — после прохождения курса нет «вау-эффекта», нет повода поделиться.

**Конкретные правки:**
- На `/cabinet` сверху — большой блок «Продолжить: <название урока>» с кнопкой.
- Привести логику ссылок к одному правилу: все курсы из кабинета ведут в `/cabinet/{slug}` (если есть кастомная) или в `/courses/{slug}/lessons/{slug}` (если нет).
- Отдавать файлы курса через защищённый эндпоинт (по аналогии с видео).
- После завершения курса показывать поздравительный экран с кнопкой «Поделиться» и ссылкой на «Личное ведение» (cross-sell).

### 2.8. `/auth/*`

**Файлы:** `login.astro`, `register.astro`, `forgot.astro`, `verify.astro`.

**Что хорошо:**
- Минималистично.
- Поддержка `?next=`.
- Валидация на клиенте простая.

**Что мешает задаче:**
1. **`verify_link_dev` и `reset_link_dev` показываются всегда** — см. 1.8. Это и баг, и утечка флоу.
2. **Нет CAPTCHA** на register/forgot. С учётом rate-limit на API это пока не критично, но при росте трафика — да.
3. **register не запрашивает имя как обязательное**. Без имени письма получаются обезличенными.
4. **На login нет «вы только что зарегистрировались, теперь войдите» сообщения** — после регистрации пользователь видит alert с dev-ссылкой и должен сам нажать «Войти». UX рваный.
5. **Один из login-URL — `/auth/login?next=...`**, другой — `/auth/login`. Стоит проверить, что в logout-flow next/после-logout логика везде сходится.
6. **Auth-страницы используют общий header с навигацией и Salyut-кнопкой** — это OK, но при ошибке формы много визуального шума.

**Конкретные правки:**
- Убрать показ dev-ссылок в production (через `import.meta.env.PROD`).
- Сделать обязательным имя при регистрации (с понятным сообщением).
- После регистрации сразу логинить пользователя (создать сессию) и редиректить в `/cabinet` с баннером «Подтвердите email, чтобы получить доступ к платному содержимому».
- Добавить «Я не получил письмо» → ссылку на повторную отправку.

### 2.9. `/salut-2026`

**Файл:** `pages/salut-2026.astro` (1295 строк, всё inline).

Это отдельный лендинг (видимо, под мероприятие/площадку). Не разбирал детально, но:

**Конкретные правки:**
