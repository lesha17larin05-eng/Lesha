# Правила работы над проектом

Этот файл — инструкция для любого агента (Claude Code и т.п.), который меняет код в этом репо. Следуй ему буквально.

---

## Главный принцип

**Любая задача = цикл: изучить → доработать → прогнать тесты → актуализировать документацию.**

Никаких изменений «вслепую» по описанию задачи. Сначала читаешь документацию и затронутые файлы — потом меняешь.

---

## Перед любой задачей (Discovery)

1. **Прочитай [docs/README.md](docs/README.md)** и пройди по разделам, релевантным задаче:
   - Auth/CSRF/JWT → `docs/03-api.md`.
   - БД, миграции → `docs/02-database.md`.
   - Frontend, страницы, middleware → `docs/04-frontend.md`.
   - Продамус, оплаты, видео-стриминг → `docs/05-payments-video.md`.
   - Тесты, как добавить новый — `docs/06-testing.md`.
   - Инфраструктура, env-переменные → `docs/01-architecture.md` + `docs/07-deploy-ops.md`.
2. **Прочитай корневой [README.md](README.md)** — там креды, Makefile-команды, общая картина.
3. **Найди затронутые файлы**:
   - Бэкенд — `api/internal/{handlers,services,db,middleware,...}`.
   - Фронт — `web/src/pages/...` и `web/src/lib/api.ts`.
   - Контракт API — `api/cmd/server/main.go` (роутер) + соответствующий handler.
4. **Прочитай существующие тесты на затрагиваемой области** — `api/internal/handlers/integration_test.go`, `*_test.go` в нужных пакетах.
5. **Не предполагай**, как что-то устроено. Если документация противоречит коду — кодом считается источник правды и документацию надо обновить (см. ниже).

## Во время доработки

- **Соответствие текущей архитектуре**. Не плоди новых пакетов/слоёв без необходимости. Структура: `handlers → services → repo (db)`. Хендлер парсит/валидирует, сервис применяет бизнес-логику (если нетривиальна), repo делает SQL.
- **SQL — только параметризованный** (pgx `$1, $2, ...`). Никакой конкатенации строк.
- **Аутентификация и доступ**:
  - Любой write-эндпоинт под `/api/` требует CSRF — middleware ставит `X-CSRF-Token` обязательным.
  - Любая мутация на фронте — через `fetch(...)`, обёртка в `Base.astro` уже подставляет CSRF.
  - Все админские действия → `repo.Audit(...)`.
- **Идемпотентность платежей**. Любая работа с webhooks Продамуса должна оставаться идемпотентной по `order_id` (повторный «paid» — no-op).
- **Видео отдаётся ТОЛЬКО через X-Accel-Redirect**. Не отдавай байты из Go.
- **Секреты — только из env**. Никогда не коммить `.env` (в `.gitignore`), никогда не логируй заголовки целиком, пароли, токены.
- **Никакого ORM**. pgx + ручные запросы.
- **Не удаляй данные** из `users`, `orders`, `payment_webhooks` — только soft-delete.
- **Изменения схемы БД — отдельной миграцией**. Не ломай совместимость существующих таблиц без `*.up.sql` + `*.down.sql`.

## Тесты — обязательны, не опциональны

После любых изменений:

```bash
make test
```

Это поднимает test-БД и прогоняет **все** Go-тесты в Docker-контейнере (см. `docker-compose.test.yml`). Все должны быть зелёными — иначе задача не сделана.

### Когда нужен новый тест

Новый тест **обязателен** при:
- Добавлении/изменении HTTP-эндпоинта → integration-тест в `api/internal/handlers/integration_test.go`.
- Изменении правил доступа (auth/admin/enrollment проверки).
- Добавлении нетривиальной бизнес-логики (расчёт прогресса, идемпотентность, подписи).
- Поиске и фиксе бага → сначала repro-тест, потом фикс.

Unit-тест предпочтителен, если логика не зависит от БД. Иначе — integration.

### Как запускать локально без контейнера

```bash
cd api
TEST_DATABASE_URL="postgres://app:app@localhost:5432/test?sslmode=disable" go test ./...
```

Без `TEST_DATABASE_URL` интеграционные тесты `t.Skip(...)` — это ожидаемо.

### Если тесты не зелёные

- **Не комитим**. Чини root cause.
- Не используй `--no-verify`, не отключай тесты.
- Если тест действительно нерелевантен после изменения архитектуры — удали его и замени новым, который покрывает текущее поведение.

## Чек-лист завершения задачи

Перед тем как считать задачу сделанной, убедись:

- [ ] Прочитал релевантные разделы `docs/` и затронутые файлы.
- [ ] Изменения соответствуют существующей архитектуре (см. правила выше).
- [ ] `make build` проходит без ошибок.
- [ ] `make test` зелёный.
- [ ] При новом/изменённом эндпоинте — есть тест, покрывающий happy path и хотя бы одну ошибку (auth/csrf/невалидный ввод).
- [ ] `docs/` обновлены под изменения (см. таблицу выше).
- [ ] Если изменения видимы пользователю — обновлён `README.md`.
- [ ] `.env.example` обновлён, если добавлены новые переменные окружения.
- [ ] Никаких секретов в коде/коммитах. `.env` в `.gitignore`.
- [ ] Хендлер вернёт корректные cookies (`access_token`, `refresh_token`, `csrf`, `auth`) и проставит CSRF, если это write-операция.

## Изображения (drop-in workflow)

Пользователь добавляет картинки **просто кладя файл в корень репо** (`/Users/richbee/Documents/GitHub/Lesha/foo.jpg` и т.п.). Дальше — твоя задача обработать.

### Правила

- Никогда не оставляй исходник в корне репо — это рабочая зона, не storage.
- Никогда не клади «сырой» исходник в `web/public/img/` — туда попадают только обработанные варианты.
- Все картинки на сайте отдаются как `<picture>` с WebP + fallback и `srcset` 1x/2x. Используй компонент [`web/src/components/ResponsiveImage.astro`](web/src/components/ResponsiveImage.astro).
- Подготовка вариантов — оффлайн через скрипт [`web/scripts/process-image.mjs`](web/scripts/process-image.mjs) (использует `sharp`). Никакой обработки на лету в SSR.
- Никаких чужих CDN/хостингов — всё локально в `web/public/img/`.

### Алгоритм при «добавь картинку»

1. Уточни у пользователя (или выведи из контекста), в какой раздел она идёт — это будет `DIR` (`hero`, `results`, `blog`, `courses`, …) и опциональный `NAME` (kebab-case slug, иначе берётся из имени файла).
2. Запусти:
   ```bash
   make img FILE=<имя файла в корне> DIR=<подпапка> [NAME=<slug>]
   ```
   Скрипт сам:
   - сгенерит `name.{jpg|png}`, `name@2x.{jpg|png}`, `name.webp`, `name@2x.webp` в `web/public/img/<DIR>/`;
   - удалит исходник из корня;
   - напечатает готовый сниппет для вставки.
3. В разметке используй компонент:
   ```astro
   ---
   import ResponsiveImage from '../components/ResponsiveImage.astro';
   ---
   <ResponsiveImage base="/img/<DIR>/<name>" ext="jpg" width="420" height="420" alt="..." loading="lazy" />
   ```
   - `ext` — `jpg` или `png` (зависит от исходника; webp берётся всегда автоматически).
   - Для hero-картинки выше первого экрана ставь `loading="eager"` и `fetchpriority="high"`.
   - `width`/`height` обязательны — иначе прыгает layout.
4. Если правишь legacy HTML (`web/src/legacy/...`) — там используй ручной `<picture>` (сниппет печатается скриптом).

### Поддерживаемые входные форматы

`.jpg`, `.jpeg`, `.png`, `.webp`. Для прозрачности — PNG, иначе JPEG (mozjpeg). Базовая ширина @2x — `min(исходная, 2400px)`, @1x = половина. Параметры можно переопределить через `--width=`, `--quality=`.

### Установка

`sharp` лежит в `web/devDependencies`. `make img` сам поднимает одноразовый `node:20-alpine` и доставит зависимость, если её нет — локально ничего ставить не нужно.

## Дизайн и вёрстка

- При любой работе по дизайну/вёрстке (новые блоки, кнопки, ссылки, карточки, иконки и т.п.) **обязательно добавляй аккуратные hover-эффекты** для интерактивных элементов.
- Hover должен быть сдержанным: плавный `transition` (обычно `150–250ms ease`), небольшое изменение цвета/фона/тени/`transform`. Никаких резких скачков, мерцаний и больших сдвигов layout.
- Состояние `:focus-visible` не забывай вместе с `:hover` — для клавиатурной доступности.
- На тач-устройствах hover не должен «залипать» — если эффект тяжёлый, оборачивай в `@media (hover: hover)`.

## Не делать

- Не использовать ORM (gorm/ent). Только pgx + ручные запросы.
- Не хранить токены в `localStorage`. Только httpOnly cookies.
- Не отдавать видео напрямую через `proxy_pass` или `sendfile` без `auth_request`/`X-Accel-Redirect`.
- Не делать собственную крипту. argon2id, JWT-библиотеки, HMAC из stdlib.
- Не использовать `customer_email` из webhook для матчинга заказа — только `order_id`/`order_num`, которые мы сами выдали.
- Не удалять записи из `users`/`orders`/`payment_webhooks`.
- Не запускать destructive команды (`make fresh`, `docker compose down -v`, `rm -rf data/`) без явного запроса от пользователя.

3. Уточни у пользователя — лучше один уточняющий вопрос, чем сделать неверно и переделывать.
